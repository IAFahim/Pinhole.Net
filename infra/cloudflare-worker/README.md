# Cloudflare code-sharing coordinator

One host, one friend, one nine-character code. The Worker pairs peers and issues
temporary Cloudflare TURN credentials. Pinhole carries encrypted application
traffic through its existing direct UDP, direct TCP or TURN path.

The owner's deployment is
**https://pinhole-coordinator.fahimmanowarj5.workers.dev**. Configure that URL on
both `PinholeHostSettings.CoordinatorUrl` and `PinholeJoinSettings.CoordinatorUrl`.
This implementation is on main; it has not been published in a new NuGet release.
The deployment has conservative quotas for development, rather than a public SLA.

## Connection flow

1. `HostAsync` creates a random code and a private 256-bit management token.
   The Worker reserves a room and generates a temporary TURN username/password.
2. Pinhole binds its sockets, gathers candidates and allocates a relay. It posts
   its full invitation, including its static public key, to the room.
3. The application displays `host.Code`; the friend calls `JoinAsync(code)`.
   The room atomically admits one joiner and issues that participant's own TURN
   credentials. A third participant receives HTTP 409.
4. The joiner gathers its candidates and posts its invitation. A hibernating
   WebSocket notifies the host immediately. HTTPS polling is the fallback if
   WebSocket upgrades are blocked.
5. Both peers dial using both invitations. This mutual exchange also establishes
   the TURN permissions needed when Cloudflare allocates different relay data IPs.
   Pinhole's existing engine chooses direct UDP/TCP or encrypted relay fallback.
6. The Worker stays out of the application data path. Registration refresh stops
   when pairing completes; the room expires, while the established session keeps
   working. Disposing either participant cleans up the registration best effort.

```csharp
var endpoint = new Uri("https://pinhole-coordinator.fahimmanowarj5.workers.dev");

// Host application:
await using var host = await PinholeSession.HostAsync(new PinholeHostSettings
{ CoordinatorUrl = endpoint });
Console.WriteLine(host.Code);
await using var peer = await host.AcceptAsync();
peer.Send("hello"u8.ToArray());

// Friend's application:
await using var friend = await PinholeSession.JoinAsync(code, new PinholeJoinSettings
{ CoordinatorUrl = endpoint });
var message = await friend.ReceiveAsync();
```

The two-process sample accepts either a Worker URL or the existing UDP directory:

```sh
dotnet run --project samples/Pinhole.CodeShare -c Release -- host https://pinhole-coordinator.fahimmanowarj5.workers.dev
dotnet run --project samples/Pinhole.CodeShare -c Release -- join https://pinhole-coordinator.fahimmanowarj5.workers.dev CODE
```

## Deploy your own copy

Run these commands inside `infra/cloudflare-worker`:

```sh
npm ci --ignore-scripts
npx wrangler login
npm test
npm run deploy
npx wrangler secret put TURN_KEY_ID
npx wrangler secret put TURN_KEY_API_TOKEN
```

Paste the TURN app's ID and API token at the respective secret prompts. They are
backend secrets, separate from the temporary username/password delivered to each
client. Do not embed the API token in the application. The deployed Worker fails
closed until both secrets are configured. The supplied configuration creates
SQLite-backed Durable Objects, which are supported on Workers Free; it does not
enable a paid plan. See [Cloudflare Durable Objects pricing](https://developers.cloudflare.com/durable-objects/platform/pricing/).

To test locally without a Cloudflare account or real relay:

```sh
npm run dev -- --port 8787 --var TURN_REQUIRED:false
dotnet run --project ../../samples/Pinhole.CloudflareProbe -f net10.0 -c Release -- --worker http://127.0.0.1:8787 --direct
```

Production clients require HTTPS. HTTP is accepted only for loopback development.

## HTTP interface

Each room operation carries `Authorization: Bearer <participant-management-token>`.
Tokens are generated by the SDK and stored as SHA-256 hashes in the room. The code
is the admission capability; it does not authorize reading or overwriting an
existing participant's invitation.

| Method | Path | Result |
|---|---|---|
| GET | `/health` | Protocol version and whether TURN secrets are configured |
| PUT | `/v1/rooms/CODE` | Claim/idempotently reopen the host's own room; host TURN credentials |
| POST | `/v1/rooms/CODE/join` | Claim the single joiner slot; joiner TURN credentials and host invitation |
| PUT | `/v1/rooms/CODE/ticket` | Update the caller's invitation; return the other participant's invitation |
| GET | `/v1/rooms/CODE/events` | Authenticated WebSocket upgrade; peer-invitation notification |
| GET | `/v1/rooms/CODE` | HTTPS polling fallback |
| DELETE | `/v1/rooms/CODE` | Either participant ends this room |

The WebSocket accepts no client application messages. Invitations are bounded to
4,096 characters, request bodies to 8 KiB, and upstream credential responses to
8 KiB. Errors are sanitized and responses use `Cache-Control: no-store`.

## Limits and trust

- Rooms expire after five minutes without an unpaired host refresh. The SDK
  refreshes every 40 seconds. A room can remain available for at most 24 hours.
- TURN credentials last 24 hours by default. This adapter does not rotate them
  during a session: establish a new session before that expiry if relay continuity
  is needed. Deleting a room removes stored credentials but does not revoke already
  issued credentials. See [Cloudflare credential lifetime guidance](https://developers.cloudflare.com/realtime/turn/generate-credentials/).
- Defaults cap room-creation attempts at 200/day and admitted room HTTP requests
  at 40,000/day, resetting at UTC midnight. Each request uses the global-budget
  Durable Object and then the room object. Per-IP rate limiting is 100/minute per
  Cloudflare location. HTTP 429 stops further admitted work; deployment limits can
  also reject requests.
- These limits bound coordination and credential issuance; they do not cap TURN
  egress bytes. Cloudflare's separate [Realtime allowance and overage pricing](https://developers.cloudflare.com/realtime/sfu/platform/pricing/)
  still apply to the account. No unlimited-free or universal-connectivity guarantee.
- The current Pinhole TURN client reaches Cloudflare over UDP (3478/443).
  Direct peer-to-peer TCP remains available. Networks that block all UDP may
  require TURN TCP/TLS support, which this change does not implement.
- The coordinator is trusted to distribute peer keys. The subsequent session is
  pinned and encrypted against those keys. For protection from a compromised
  coordinator, share the full invitation or compare an invitation fingerprint
  out of band; short codes alone are not a PAKE. See [host/join trust model](../../docs/HOST_JOIN.md).
- MoQ remains a separate optional publish/subscribe transport. This coordinator
  does not require MoQ, WebRTC, Rust or an FFI bridge.

Explicit `NodeOptions.Relays = []` disables TURN allocation. Explicit relay or
STUN lists take precedence over the coordinator's supplied defaults. Setting
`EnableDirectUdp = false` and `EnableTcpTransport = false` forces TURN for testing
and fails if allocation is unavailable.

## Verification

`npm test` covers ownership, concurrent admission, expiry, budgets, payload limits,
credential caching and sanitized upstream failures. The C# tests use real encrypted
peers with HTTP polling and a strict fake TURN server with separate data addresses.
CI also runs the actual local Worker with both .NET runtimes to exercise WebSockets.

The live probe emits only metrics and invitation hashes:

```sh
dotnet run --project samples/Pinhole.CloudflareProbe -c Release -f net10.0 -- --worker https://pinhole-coordinator.fahimmanowarj5.workers.dev
dotnet run --project samples/Pinhole.CloudflareProbe -c Release -f net10.0 -- --worker https://pinhole-coordinator.fahimmanowarj5.workers.dev --relay
```
